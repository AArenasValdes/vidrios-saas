# Plan: Pasada final de hardening y readiness para lanzamiento

## Contexto

Estamos en la fase final de preparacion para lanzamiento real del SaaS Ventora. El objetivo es una pasada conservadora de hardening sobre las partes mas criticas, sin abrir Fase 3+ ni realizar refactors amplios.

## Estado base actual (2026-05-13+)

- `npm run lint`, `npm test` y `npm run build` pasan en el workspace principal.
- Rutas publicas `/solicitud/[empresa]` y `/presupuesto/[token]` ya fueron endurecidas en pasadas anteriores.
- Auth helper comun resuelve primero por `auth_user_id` y cae a correo por compatibilidad.
- `proxy.ts` ahora cubre `/solicitudes` y `/configuracion/*`.
- `web_push_subscriptions` ya tiene RLS policies.
- Cache publico de landing ahora invalida correctamente via `/api/public-landing/revalidate`.

## Hallazgos rapidos de riesgo (de la revision)

1. **Auth y session:**
   - `useAuth.ts` mantiene un timeout fijo de 8s (`AUTH_RESOLVE_TIMEOUT_MS`). Si Supabase tarda mas, el hook cae a estado no autenticado aunque la sesion sea valida.
   - `useAuth.ts` tiene un `useEffect` vacio `[]` que llama `resolveAuthState()` sin manejo de cancelacion de race condition si cambia `organizacionId` rapidamente.
   - El `signOut` en `useAuth.ts` restaura `previousState` si falla, lo que puede dejar al usuario en un estado "pseudo-logout" en UI mientras la sesion sigue activa.

2. **Rutas publicas criticas:**
   - `/solicitud/[empresa]`: Cumplimiento de `is_published` ya esta implementado, pero falta verificar si el rate limiting por IP es suficiente bajo ataque distribuido.
   - `/presupuesto/[token]`: El `unstable_cache` en `publicCotizacionApprovalService.resolveByToken` podria servir datos obsoletos si se aprueba/rechaza via server action y el cache no se invalida correctamente en todas las replicas. `safelyRevalidatePublicApprovalQuotesCache` ya captura errores de runtime, pero la consistencia final depende de Next.js.

3. **Dashboard y bootstrap inicial:**
   - `dashboard/summary` API usa `resolveAuthenticatedRouteContext`, no hay riesgo de filtrado multi-tenant. OK.
   - Si un usuario logueado pierde la conexion momentaneamente, las pantallas pueden entrar en un estado de "loading skeleton" interminable porque `useCotizacionesStore` y otros hooks no tienen timeout de red ni retry backoff.

4. **Cotizaciones - guardado:**
   - `saveWorkflow` en `useCotizacionesStore.ts` usa `requestKey` para evitar duplicados, pero si falla la segunda etapa despues de crear cliente/proyecto, la funcion `rollbackEntities` solo hace soft delete de clientes, no de proyectos. Esto puede dejar proyectos huerfanos si el guardado de la cotizacion principal falla.
   - `cotizacionesAppService.saveWorkflow` no tiene timeout explicito ni manejo de errores de red diferenciado (solo try/catch generico).
   - El generador de codigo `reserveNextCode` depende de una funcion DB `reserve_next_cotizacion_code`. Si la DB devuelve error de simultaneidad, no hay retry.

5. **Multi-tenant y Queries:**
   - Los repositories siempre filtran por `organization_id`. OK.
   - El admin client (`createAdminClient`) se usa en `/api/auth/profile` y en repositorios publicos sin verificar el `organization_id` en contexto de app; eso es intencional porque son operaciones cross-org, pero debe mantenerse asi.

6. **Supabase Client vs Server:**
   - `src/lib/supabase/client.ts` usa `process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!` sin manejar el caso de que no exista. En local si esta, en prod Vercel tambien, pero al hacer build estatico o en tests podria fallar.
   - `src/lib/supabase/server.ts` captura el error de set cookies pero no invalida la sesion. Esto puede causar loops de login si las cookies no se escriben.

7. **Estados de carga y vacios:**
   - En `/cotizaciones/nueva/page.tsx` el `useEffect` de persistencia guarda en `sessionStorage` sin try/catch si esta full.
   - En `/cotizaciones/nueva/page.tsx` si `loadCotizacionById` falla al duplicar/editar, se queda en loading sin mensaje claro.
   - AppShell (`app-shell.tsx`) no tiene fallback si `useAuth` devuelve `cargando: true` por mas de X segundos.

8. **Errores silenciosos y race conditions:**
   - `prefetchCotizacionById` en `useCotizacionesStore` usa `try { await loadCotizacionById(id) } catch { return null }`. Esto silencia errores reales de permisos o conexion.
   - `useCotizacionesStore.refreshCotizaciones` tiene una race condition potencial si cambia `organizacionId` mientras una request esta en vuelo: usa `activeRefreshIdRef` pero `ensureClientesLoaded` se llama despues sin el mismo ref.

9. **Configuracion Empresa/Pagina Venta:**
   - `useOrganizationProfile` depende de `useAuth`. Si `useAuth` devuelve `cargando: true` por mucho tiempo, la pagina de configuracion se queda en skeleton.
   - Upload de logo/hero ahora pasa por server-side (`/api/organization-assets/upload`), lo cual es correcto. Pero si falla esa API, la UI muestra un mensaje generico.

## Plan de accion (priorizado por riesgo)

### Fase 1: Auth y bootstrap (Riesgo Alto)

1. **Ajustar timeout de auth y evitar loops**:
   - En `src/features/auth/hooks/useAuth.ts`, incrementar `AUTH_RESOLVE_TIMEOUT_MS` de 8000ms a 15000ms y agregar un retry simple con backoff (1 intento extra a los 3s) si la primera peticion falla por timeout o conexion.
   - Agregar ` AbortController` en `resolveAuthState` para cancelar el timeout si el componente se desmonta.
   - En `useAuth.ts signOut`, cambiar el rollback de `previousState` a `unauthenticatedState` para evitar rebounds de sesion.

2. **Manejo robusto de errores de login**:
   - En `app/(auth-public)/login/login-view.tsx`, agregar mensaje explicito si `get_org_id` devuelve permission denied (ya detectado en tests, pero falta en UI real).
   - Asegurar que el `next` query param persista despues de login exitoso.

### Fase 2: Rutas publicas criticas (Riesgo Alto)

3. **Endurecer rate limiting en `/api/solicitud/[empresa]`**:
   - El rate limit actual es por IP en memoria. Evaluar si es suficiente; por ahora, agregar un control de cabecera `X-Forwarded-For` para evitar spoofing simple si esta detras de proxy.

4. **Cache de aprobacion publica consistente**:
   - En `src/features/cotizaciones/public-approval/services/public-cotizacion-approval.service.ts`, asegurar que `accept` y `reject` invaliden el cache explicitamente. Evaluar anadir `no-cache` en el header de la respuesta del server action para forzar fresh read.
   - En `app/presupuesto/[token]/actions.ts`, verificar que `revalidatePublicApprovalQuotesCache` se ejecuta SIN fallar silenciosamente.

### Fase 3: Cotizaciones - robustez de guardado (Riesgo Alto)

5. **Rollback completo en saveWorkflow**:
   - En `src/features/cotizaciones/services/cotizaciones.service.ts`, modificar `rollbackEntities` para incluir `projectRepo.softDelete` si el proyecto fue creado pero la cotizacion fallo.
   - Agregar timeout a `saveWorkflow` para evitar requests colgadas indefinidamente.

6. **Manejo de errores de conexion y reintentos**:
   - En `useCotizacionesStore.ts`, wrappear `saveWorkflow`, `deleteWorkflow`, `updateManualResponseStatus` con un retry de 1 intento si el error es de conexion (`isConnectivityError`).
   - En `useCotizacionesStore.ts`, agregar un estado `saveError` para que la UI pueda mostrar un mensaje de error persistente en vez de quedar en `isSaving: true`.

### Fase 4: Estados de carga, vacios y mecanismos de cancelacion (Riesgo Medio)

7. **Timeouts y cancelaciones**:
   - En `useCotizacionesStore.ts`, agregar un maximo de 30 segundos para `loadCotizacionById` y `refreshCotizaciones` antes de forzar `setIsReady(true)` y `setError("timeout")`.
   - En `app/(pwa-app)/cotizaciones/nueva/page.tsx`, agregar un `useEffect` cleanup para `persistenciaWizard` si el usuario navega fuera antes de que termine la persistencia.

8. **Pantalla de error generica en AppShell**:
   - En `src/components/layout/app-shell.tsx`, agregar un estado de "Sin conexion" o "Error de conexion" visible si `useAuth` esta atascado en `cargando: true` por mas de 10 segundos.

9. **Manejo de storage lleno en nueva cotizacion**:
   - En `app/(pwa-app)/cotizaciones/nueva/page.tsx`, wrappear `sessionStorage.setItem` en try/catch y mostrar un toast/mensaje si `QuotaExceededError`.

### Fase 5: Multi-tenant y seguridad adicional (Riesgo Medio)

10. **Auditar clientes vacios**:
   - Verificar que `createClientesRepository.ts` no retorne `null` en `findByNombre` si hay soft delete. Confirmar que siempre filtra `eliminado_en IS NULL`.

11. **CSP y headers**:
   - Anadir `Content-Security-Policy` basico en `next.config.js` para prevenir XSS en `/solicitud/[empresa]` y `/presupuesto/[token]`.

### Fase 6: Tests y verificacion final (Riesgo Bajo - obligatorio)

12. **Tests**:
   - Agregar test para el flujo de rollback de `saveWorkflow` con proyecto huerfano.
   - Agregar test para `useAuth` timeout y cancelacion.
   - Corregir tests existentes si los cambios de codigo rompen contratos.

13. **Verificacion obligatoria**:
   - `npm run lint`: verificar que no hay errores nuevos.
   - `npm test`: verificar que todos los tests pasan.
   - `npm run build`: verificar que el build de produccion compila sin errores.
